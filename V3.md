# Gigi: Agentic City RAG Assistant — Architecture and Implementation Plan

Status: design settled through review. Existing-component tweaks are specified against the supplied code (section 6). Deployment and infrastructure are listed as prerequisites only (section 8), not built by this plan.

---

## 1. Scope

Reused as-is (existing build):
- Crawl, chunk, and embed pipeline: `website_crawler.py`, BGE-large via `sentence-transformers`, ChromaDB persistent store.
- Classifier: `classify.py` (retention labels; not consulted at query time).
- `rag_embeddings.py`: the shared embedding contract used by crawler and query path.

New build (this plan):
- FastAPI backend orchestrating the agentic retrieve, draft, fetch, verify loop, with all Anthropic calls server-side.
- Lit single-page app ("Gigi") served from `gigi.ggcity.org`.
- A vanilla JavaScript companion script injected into the Drupal template, running on every city page.
- One SQLite file for session state, fetched-page cache, rate-limit counters, and interaction logging.

Existing components are refactored onto a shared library reused by the crawler, the retained Gradio app (kept for backend testing), and the new backend. Tweaks are specified in section 6, the library in section 7.

Optimization target, carried from the design discussion: honest "not found" plus human redirect over confident-but-unsupported answers. Low false positives are weighted above answer coverage.

## 2. Architecture

### 2.1 Components

- Gigi app (Lit), built to static assets and served by the FastAPI backend, reached through your proxy at the Gigi origin: chat UI, streaming, tile layout and animation, narration. Talks to the backend over a WebSocket. Does not read iframe DOM.
- Companion script (vanilla JS, in the Drupal template): runs inside each city page. Receives a verified quote, fuzzy-matches it in its own DOM, highlights via the CSS Custom Highlight API, scrolls, and reports a miss if it cannot find the quote.
- FastAPI backend (Python): query rewrite, retrieval, draft, live page fetch, verification, branch logic, logging, rate limiting. Holds the Anthropic key. It also serves the Lit static bundle, and is fronted by your existing proxy (the one serving Drupal), so there is no separate static host.
- SQLite (one file, WAL mode): sessions, interaction log, model-call log, verification log, retrieval log, page cache, rate limits.
- Existing retrieval stack: BGE-large query embedding via `rag_embeddings.py`, ChromaDB similarity search.
- Models: Haiku for follow-up rewrite and per-claim verification; Sonnet for the structured draft and the single capped regen.

### 2.2 Origin and communication model

Gigi lives on a subdomain, which is cross-origin to the city site, so the parent never reads the framed page. The companion does all in-page work from inside its own origin. Two channels carry intent to the companion:

- postMessage, for desktop tiles: the parent posts the verified quote to the iframe's window. The companion validates `event.origin === 'https://gigi.ggcity.org'` before acting, and Gigi validates replies. Origin checks are mandatory.
- Hash fragment, for standalone or mobile opens with no parent: the quote rides in `/path#gigi={encoded}`. Fragments never reach the server, so they do not fragment CDN or Drupal cache, do not appear in logs or analytics, and create no distinct cacheable URL. The companion reads `location.hash` and strips it via `history.replaceState` after reading.

Cross-origin framing requirement: the city pages must send CSP `frame-ancestors 'self' https://gigi.ggcity.org`. `X-Frame-Options: SAMEORIGIN` will not allow a different subdomain to frame the main site and cannot name a single other origin, so it should be dropped in favor of the CSP directive. This is a prerequisite (section 8), not a build step. If you instead serve Gigi at a same-origin path behind the proxy (for example `/gigi`) rather than the subdomain, `frame-ancestors 'self'` alone suffices and the parent could read the iframe directly; the companion still works either way and is kept for the mobile path regardless.

### 2.3 Request lifecycle

1. User sends a query. Gigi shows a holding state instantly ("One moment while I look this up"). No model call; this is where progress narration streams in.
2. Backend rewrites the follow-up into a standalone query (Haiku). Conversation context is the recent interactions for the session (section 2.6), capped.
3. Retrieve top-k chunks from Chroma. This yields ranked candidate URLs and chunk text.
4. Sonnet drafts the answer from the retrieved chunks in the structured claim-tagged format (section 4), with citations. If the chunks support nothing, Sonnet abstains here and the turn goes straight to not-found plus redirect.
5. Backend fetches the live pages for the cited URLs only, not all top-k. Parse to text, write to the page cache with a TTL.
6. Haiku verifies each cited claim against its fetched live page text, returning supported-or-not plus a verbatim quote. Verifying against the freshly fetched full page is a more independent check than re-reading the chunk Sonnet drafted from, which is why the fetch is retained even with low staleness.
7. Branch (section 2.4).
8. Stream the finalized answer to Gigi, replacing the holding state. The answer streams even though verification delayed its start.
9. Gigi opens the cited links as tiles (capped count), posting each verified quote to that page's companion; hash fragment for standalone or mobile.
10. The companion highlights and scrolls to the verified quote in its own DOM, or reports a miss.
11. Gigi narrates the result through an `aria-live` region.

### 2.4 Failure handling

The draft's claim-to-source map (section 4) makes targeted failure handling possible. On a verification failure:

- Single capped regen, informed by the verification result. The regen prompt includes the original context plus the verification signal: which claim failed and what the live page actually says. Without that signal in the prompt the regen reproduces the same answer. Cap is one regen per turn.
- Re-verify the regen, then stop. Flow: draft, verify, fail, informed regen, verify again. The re-verify reuses the cached page text, so it costs one Haiku call, not another fetch.
- Floor when the single regen still fails: soften or drop the affected segments, or fall to not-found plus redirect. Softening is a backend operation, not a model regeneration: the backend rewrites or annotates only the segments whose supporting sources all failed, leaving verified segments untouched. For a public-sector tool, prefer a fixed comms-approved disclaimer template over a model-phrased hedge, for consistent reviewable wording and zero extra tokens.
- Abandon threshold: if a primary segment fails or too many segments fail, drop the whole answer to not-found plus redirect rather than serve a partial answer. The backend reads this from the map.
- Cost ceiling per turn is fixed by design: at most one extra Sonnet call and one extra Haiku pass. Rare failures make it cheaper; they do not make it unbounded.

The not-found message is scoped to "I could not find this on the city site," never "this does not exist," and routes to a real human contact.

### 2.5 Transport

WebSocket, because a turn is bidirectional within itself: query up, narration and answer tokens down, tile-open instructions down, companion miss-reports up, narration down. The Anthropic key never leaves the server. Event types over the socket: `narration`, `answer_token`, `answer_done`, `open_tiles`, `tile_result`, `not_found`. The companion-miss report comes back up as a client event the backend can act on (soften that tile).

### 2.6 Data model (SQLite, WAL mode, busy_timeout set)

Single source of truth: session history is derived from recent interactions, not duplicated.

- `sessions(session_id TEXT PK, created_at, last_seen_at)`
- `interactions(interaction_id TEXT PK /* uuid4 */, session_id, created_at, user_query, rewritten_query, outcome /* answered | softened | regenerated | not_found */, final_answer, citations JSON, regen_count INT, tokens_in INT, tokens_out INT, latency_ms INT)`
- `model_calls(id INTEGER PK, interaction_id, seq INT, call_type /* rewrite | draft | verify | regen */, model, tokens_in, tokens_out, latency_ms, prompt JSON, response JSON, created_at)`
- `verifications(id INTEGER PK, interaction_id, source_url, claim, verified INT, quote, page_cache_hit INT, fetch_latency_ms, created_at)`
- `retrievals(id INTEGER PK, interaction_id, rank INT, chunk_id, url, score REAL)`
- `page_cache(url TEXT PK, text, fetched_at, ttl_seconds)`
- `rate_limits(key TEXT PK /* ip or session */, window_start, count)`

Indexes: `interactions(session_id, created_at)`, `model_calls(interaction_id)`, `verifications(interaction_id)`, `retrievals(interaction_id)`. Every generation is logged in `model_calls` and tied to its `interaction_id`. The interaction uuid is surfaced to the frontend for support reference.

### 2.7 Accessibility (target: WCAG 2.1 AA, due April 26, 2027 for Garden Grove)

The chrome Gigi owns must meet the standard; the framed city pages are the city's own responsibility and independently in scope.

- Status messages (4.1.3): narration through `aria-live="polite"`.
- Streaming: render answer tokens visually, announce the completed answer once. Do not pipe every token into the live region.
- Frame titles (4.1.2): each tile iframe has a unique descriptive `title`.
- Focus order (2.4.3): do not move focus into a tile on open or lose it on close; keep focus in the chat, let the user enter a tile by choice.
- Color and non-text contrast (1.4.1, 1.4.11): the highlight uses more than color (underline or border) and meets contrast; the cited link in the answer is the accessible path to the same place.
- Keyboard (2.1.1): open, close, move between tiles, and the input, all operable without a mouse.
- Reduced motion: gate the centered-to-side and tile animations behind `prefers-reduced-motion`.
- Testing is manual plus automated; automated scanners catch only a fraction of issues.

### 2.8 Mobile

Chatbot only, no iframes, no tiles. Citations open the city page directly with a `#gigi=` hash, and the companion highlights there. This supersedes text fragments, which can be dropped. Standard chat accessibility applies; descriptive link text (2.4.4). Touch target sizing is good practice but is a WCAG 2.2 criterion, not part of the 2.1 AA mandate.

### 2.9 Text normalization parity (load-bearing)

The crawler's HTML extraction strips `script`, `style`, `nav`, `footer`, and `header`, takes the main or article or `.content` region (falling back to body), joins text across elements with single spaces, and collapses all whitespace with `re.sub(r"\s+", " ", text)`. The stored chunk is therefore a normalized, structurally flattened projection of the page, not a literal slice of the live DOM. Three consequences the build must respect:

- The backend's live fetch for verification uses the same extraction functions (section 7), so the verifier reads text consistent with the chunks.
- The companion, matching in the live DOM, must apply the same whitespace collapse to the live text before fuzzy-matching the verifier's quote, and should search within the same content root (main or article or `.content`) rather than the whole document, so it does not match stripped boilerplate. Without this, the quote (whitespace-collapsed, boilerplate-free) will not be found in the raw DOM.
- The crawler injects a `Title:` prefix into some chunks; that text does not exist on the page, so it must never be chosen as a highlight quote.

This is why the highlight target is the verifier's short quote fuzzy-matched live, not the stored chunk matched directly: the chunk is normalized and cannot be matched verbatim.

## 3. Key decisions and tradeoffs

- Subdomain plus companion, not same-origin proxy. Removes the cross-origin DOM read and keeps Gigi isolated on its own subdomain. Cost taken on: a script on every page (a larger security-review and critical-path item) and a cross-origin framing allowance.
- Backend fetch and verify, not client-side extraction. Restores a verify gate before the answer is sent and gives an independent full-page check. Cost: per-query fetch latency and CMS load, mitigated by the page cache.
- Single capped regen, informed by the verification result, with a soften/not-found floor. Bounds the failure cost and avoids the regen loop.
- SQLite, not Redis. One file for session, cache, limits, and logs; fits the minimal-infra, data-local posture. Boundary: single machine; multi-machine scale-out would need a different store.
- Lit, not React or Vue. Standards-based, tiny runtime, OpenJS-governed. Cost: smaller ecosystem and a more manual animation story (Motion's declarative layout props are React-only; in Lit you use Motion's imperative `animate()`, the View Transitions API, or a hand-rolled FLIP).
- Structured claim-tagged draft format (section 4) is load-bearing. It is what makes targeted softening and informed regen possible. Opaque prose would force full regen.

Where this plan is opinionated: it is tuned for low false positives and honest abstention. If coverage is later prioritized over abstention, loosen the verifier, raise the cited-source count, and lean on regen over not-found, in that order.

## 4. Structured draft format

Sonnet emits the answer as segments, each tagged with the source ids that support it, so the backend can target individual claims during verification handling.

```json
{
  "segments": [
    { "id": "s1", "text": "City Hall is open Monday through Friday.", "source_ids": ["src2"] },
    { "id": "s2", "text": "Passport services require an appointment.", "source_ids": ["src5"] }
  ],
  "sources": [
    { "id": "src2", "url": "https://www.ggcity.org/cityhall", "label": "City Hall hours" },
    { "id": "src5", "url": "https://www.ggcity.org/passports", "label": "Passport services" }
  ],
  "abstain": false
}
```

Rules: every factual segment carries at least one source id; an empty `source_ids` on a factual segment is itself a failure to handle; `abstain: true` short-circuits to not-found. Verification marks each source pass or fail; the backend then finds segments whose sources all failed and applies the section 2.4 handling.

## 5. Phased implementation plan

### Phase 0 — Prerequisites (gate, not built here)
Infra sign-off must clear before Phase 3 can integrate. See section 8.

### Phase 1 — Backend orchestration core (testable without any UI)
- FastAPI skeleton; WebSocket endpoint; event protocol (section 2.5).
- SQLite schema and migrations; WAL and busy_timeout; logging writers for interactions, model_calls, verifications, retrievals.
- Import `shared/rag_core` and `shared/extraction`; do not reimplement retrieval or extraction (section 7).
- Reuse query embedding and Chroma retrieval from the core; capture Chroma ids for the `retrievals` log.
- Haiku rewrite (from the core); session history derived from recent interactions.
- Sonnet structured claim-tagged draft (section 4) with abstention, using the new draft prompt (the existing prose prompt stays with the Gradio harness).
- Live page fetch for cited URLs; page_cache with TTL.
- Haiku verify per cited claim; branch logic (pass / informed single regen + re-verify / soften / not-found).
- Rate limiting against `rate_limits`.
- Harness: drive the socket with a CLI or wscat to validate the full loop and the logs before any frontend exists.

### Phase 2 — Lit Gigi app
- Chat UI, message list, WebSocket client, streaming consumption.
- Holding state and progress narration wired to `aria-live`.
- Centered single-column layout (pre-tiling).
- Render finalized answer, citations, and not-found/redirect states.
- Surface the interaction uuid for support reference.

### Phase 3 — Companion, tiling, highlight (requires Phase 0)
- Companion (vanilla): origin-checked postMessage and hash-fragment intake; TreeWalker text index over the main content root with the same whitespace collapse as the crawler (section 2.9); fuzzy match the verifier quote; Range; Custom Highlight API with a single-node span fallback; scroll; miss reporting. Defensive and tiny.
- Tiling in Gigi: open cited URLs as iframes in a CSS grid with `gap` and rounded wrappers (`overflow: hidden`); centered-to-side morph and tile open/close animation (Motion `animate()` or View Transitions), gated by `prefers-reduced-motion`; tile cap; announce tile close.
- Quote delivery to companion; handle companion miss by softening that tile.

### Phase 4 — Mobile
- Chatbot-only layout; citation links open `#gigi=` deep links; companion highlights on the destination page; no tiles; remove text-fragment path.

### Phase 5 — Hardening and accessibility
- WCAG 2.1 AA audit (manual plus automated) and remediation across section 2.7.
- Abuse protection, request size caps, spend monitoring and alerts.
- Concurrency: multiple uvicorn workers behind the host (GIL-bound query embedding); confirm SQLite WAL behavior under worker write load; load test.
- Log retention and PII handling policy (section 8).

### Suggested repository layout
```
shared/

  store.py            # SQLite: schema, logging, sessions, cache, limits
  prompts/            # structured draft, rewrite, verify, regen
crawler/
  website_crawler.py  # imports shared/extraction + shared/rag_embeddings
  classify.py         # unchanged
gradio_app.py         # thin UI over shared/rag_core, kept for testing
frontend-gigi/        # Lit app, built to static assets served by the backend
companion/            # vanilla JS injected into the Drupal template
```

## 6. Existing-component tweaks (specified against supplied code)

The RAG logic in `city_chatbot.py` is already cleanly separable; only thin Gradio glue is coupled. The crawler and embedding helper need small additions, not rewrites.

`rag_embeddings.py` (no change): `Embedder`, `sanitize_metadata`, and `fetch_all` are reused as-is. The query path imports `Embedder` exactly as the chatbot does today.

`city_chatbot.py`, refactored into the shared core (behavior preserved):
- Move `rewrite_query`, `search_knowledge_base`, `format_context_and_sources`, and `generate_response` into `shared/rag_core` (section 7). These are already UI-free.
- Leave `create_gradio_interface`, `chat_with_rag`, and `_normalize_history` in a thin Gradio wrapper that imports the core, so the Gradio app keeps working for backend testing.
- `search_knowledge_base` currently discards the Chroma document ids. Capture `response["ids"][0]` alongside documents and metadatas so the orchestrator can log `chunk_id` in the `retrievals` table. One-line addition.
- The current `SYSTEM_TEMPLATE` emits prose with inline markdown links. The agentic backend needs the structured claim-tagged format (section 4) instead, so add a second draft prompt and keep the existing one for the Gradio harness. The abstention rule and the ggcity.org-only rule carry into the new prompt.
- Minor: the system prompt hard-codes "Today is June 18, 2026." Make the date dynamic in the core.

`website_crawler.py`, refactored for shared extraction (plus one optional addition):
- Move `extract_text_from_html`, `extract_text_from_pdf`, `extract_text_from_docx`, and `chunk_text` into `shared/extraction` (section 7). The backend's live fetch for verification must call these same functions, or the verifier reads differently-normalized text than the chunks were built from (section 2.9).
- The crawler prepends `Title: {title}` to chunks that do not begin with the title. That injected text is not on the live page, so the draft and verifier must never select a highlight quote from it.
- PDF page mapping (optional, only if PDF page deep links matter): the crawler concatenates PDF pages with newlines and stores `page_count` but no per-page boundaries, so a chunk cannot be mapped back to a page number for `#page=N`. If you want that, store per-page text or page offsets during the crawl.

`classify.py` (no query-time change): stays decoupled; the chatbot already ignores classification labels at query time.

## 7. Shared library and code reuse

Goal: one copy of any logic that must not drift between indexing, the Gradio test harness, and the new backend. This is the answer to "pull what you need or make a shared library": make the library, refactor both existing entry points onto it, and keep Gradio for testing.

Modules:
- `shared/rag_embeddings.py` (existing, unchanged): `Embedder`, `sanitize_metadata`, `fetch_all`.
- `shared/extraction.py` (new, from the crawler): `extract_text_from_html`, `extract_text_from_pdf`, `extract_text_from_docx`, `chunk_text`. Used by the crawler at index time and by the backend's live fetch at verify time, so normalization is identical (section 2.9).
- `shared/rag_core.py` (new, from the chatbot): rewrite, retrieval, context and source formatting, generation, with no UI dependency. Imported by both the Gradio app and the FastAPI backend.

Consumers:
- `crawler/website_crawler.py`: imports `shared/extraction` and `shared/rag_embeddings`; otherwise unchanged.
- `gradio_app.py` (refactored `city_chatbot.py`): thin UI over `shared/rag_core`, retained for backend testing, not deployed to residents.
- FastAPI backend: imports `shared/rag_core` and `shared/extraction`, and adds the agentic loop (live fetch, verify, branch), the structured draft prompt, SQLite logging, and the WebSocket protocol on top.

The single most important reason to share `extraction` rather than reimplement it: verification and highlighting line up only if the verifier reads text normalized the same way the chunks were built. Sharing the function removes that risk by construction.

## 8. Prerequisites (infrastructure, not built here)

- Proxy routing on your existing proxy (the one fronting Drupal) to the FastAPI backend, which serves both the Gigi static bundle and the API/WebSocket. No separate static host.
- Decision on Gigi's origin: a subdomain (`gigi.ggcity.org`) or a same-origin path (`/gigi`). This sets the `frame-ancestors` value below and whether the companion is strictly required; it is kept regardless for the mobile path.
- Drupal template injection of the companion script, with security review for a script that runs on every page.
- City pages sending CSP `frame-ancestors` that allows the Gigi origin (`'self'` if a same-origin path, `'self' https://gigi.ggcity.org` if a subdomain), and dropping any conflicting `X-Frame-Options`.

## 9. Risks and open items

- Log PII under AR 2.16. Logging raw user queries makes the interaction log a PII store even though crawled pages have none, because residents volunteer PII in free text. Requires a retention policy, access controls, and likely redaction on the query field. Reference: AR 2.16 (Cloud Computing Services Policy), https://internal.ggcity.org/policies.
- Framing-header approval. If the city cannot allow the subdomain to frame the main site, the desktop tiling design falls back to the mobile links-only experience.
- Custom Highlight API support. Broadly supported in current Chromium and Safari; verify against the browsers residents actually use and keep the span fallback.
- Server-rendered vs JS-rendered divergence. Backend-fetched HTML can differ from the browser-rendered DOM on JS-built sections; Drupal is mostly server-rendered, but handle the companion miss path.
- Single-machine SQLite boundary. Fine at pilot scale; multi-machine scale-out needs a different store or shared filesystem.
- Animation in Lit is manual. Budget time for the centered-to-side and tile transitions without Motion's declarative layout props.
