# Gigi: Agentic City RAG Assistant — Architecture and Implementation Plan

Status: design settled through review. Existing-component tweaks are specified against supplied code (section 8). Deployment and infrastructure are prerequisites only (section 10), not built here. High-load scaling is deferred by decision, noted in risks.

Optimization target, carried throughout: honest "not found" plus human redirect over confident-but-unsupported answers. Low false positives are weighted above answer coverage.

Build note (pipeline rewritten for responsiveness — supersedes the gated design below). The verify-before-show approach forced a full structured draft to generate before any text could appear (~12s of dead air), which fails the responsiveness bar. The pipeline is now a **single streaming mode**:

- **Verify mode and the structured claim-tagged draft are removed.** No gate, no regen, no not-found-on-failure, no pre-answer Haiku pass.
- **The answer streams token-by-token.** On a follow-up turn (history present) a small Haiku call rewrites the message into a standalone **retrieval** query (the v2 rewrite, reused from `shared/rag_core` so the prompt can't drift; language-agnostic — references are resolved by the model, not a word list); the first turn retrieves on the raw message. Either way Sonnet then streams a prose answer with inline `[title](url)` citations via the async Anthropic stream API, given the **original** message plus the conversation history (so it resolves the follow-up itself — the rewrite only feeds the embedder). First token ~1s on the first turn; a follow-up adds one small Haiku call before retrieval.
- **The frontend opens tiles** by parsing the streamed markdown links itself (no backend `open_tiles`, no allowlist). Multi-turn tile lifecycle (replace on a new cited answer, keep when none) is a frontend concern.
- **Highlighting is a non-blocking, post-answer enhancement (on by default, `HIGHLIGHT_ENABLED`).** After `answer_done`, the backend fetches the cited pages, asks Haiku for the verbatim span, snaps it to a true substring, and emits a `highlight {url, quote}` event per cited page. The companion highlights + reveals the tab in the already-open tile (no scroll).
- **SSRF guard:** the backend only fetches model-cited URLs whose host is in `ALLOWED_FETCH_HOSTS` (default `ggcity.org`), and only those also in the retrieved source set.

The original gated design (sections 2.3–2.5 below, the structured format in section 4) is kept for historical context but is no longer what runs; deltas are flagged inline.

## 1. Scope

Reused as-is (existing build):
- Crawl, chunk, embed pipeline: `website_crawler.py`, BGE-large via `sentence-transformers`, ChromaDB.
- Classifier: `classify.py` (retention labels, not consulted at query time).
- `rag_embeddings.py`: the shared embedding contract.

New build (this plan):
- FastAPI backend orchestrating the agentic retrieve, draft, fetch, verify loop. All Anthropic calls server-side. It also serves the Gigi static bundle and sits behind your existing proxy (the one fronting Drupal), so there is no separate static host.
- A standalone, WCAG-first chat UI module (handrolled in Lit), reusable outside Gigi (section 5).
- The Gigi app shell (Lit): morph, tiles, narration wiring, WebSocket, embeds the chat module.
- A vanilla companion script injected into the Drupal template, running on every city page.
- One SQLite file for session state, fetched-page cache, rate-limit counters, and interaction logging.

Existing components are refactored onto a shared library reused by the crawler, the retained Gradio app (kept for backend testing), and the new backend. Tweaks in section 8, library in section 9.

## 2. Architecture

### 2.1 Components

- Chat module (Lit, standalone): message list, input, streaming render, markdown with sanitization, a narration live region, and full keyboard and screen-reader support. Knows nothing about transport or tiles; the shell drives it through a small imperative API (section 5).
- Gigi app shell (Lit, `gigi` origin): owns the WebSocket, the centered-to-side morph, the tiled iframes, and routing of backend events. Embeds the chat module and feeds it.
- Companion script (vanilla JS, in the Drupal template): runs inside each city page, receives a verified quote, reveals the containing Bootstrap tab or collapsible if needed, fuzzy-matches the quote in its own DOM, highlights via the CSS Custom Highlight API, scrolls, and reports a miss.
- FastAPI backend (Python): rewrite, retrieval, draft, live fetch, verification, branch logic, logging, rate limiting. Holds the Anthropic key. Serves the Gigi static bundle.
- SQLite (WAL): sessions, interaction log, model-call log, verification log, retrieval log, page cache, rate limits.
- Retrieval stack: BGE-large query embedding via `rag_embeddings`, ChromaDB similarity search.
- Models: Haiku for rewrite and per-claim verify, Sonnet for the structured draft and the single capped regen.

### 2.2 Origin and communication model

Gigi runs on its own origin (a subdomain such as `gigi.ggcity.org`, or a same-origin path such as `/gigi`), proxied by your existing proxy. The FastAPI backend serves the static bundle and the API and WebSocket. Because Gigi never reads the framed page, the companion does all in-page work from inside its own origin. Two channels carry intent to the companion:

- postMessage, for desktop tiles: the shell posts the verified quote to the iframe window. The companion validates `event.origin` against the Gigi origin before acting, and the shell validates replies. Origin checks are mandatory.
- Hash fragment, for standalone or mobile opens with no parent: the quote rides in `/path#gigi={encoded}`. Fragments never reach the server, so they do not fragment cache, do not appear in logs or analytics, and create no distinct cacheable URL. The companion reads `location.hash` and strips it via `history.replaceState`.

Cross-origin framing: if Gigi is on a subdomain, the city pages must send CSP `frame-ancestors 'self' https://gigi.ggcity.org` and drop any conflicting `X-Frame-Options`. If Gigi is on a same-origin path, `frame-ancestors 'self'` suffices. Prerequisite, section 10.

### 2.3 Request lifecycle (current — streaming)

1. User query. The shell shows a holding state immediately and starts narration. No model call.
2. Retrieve top-k chunks from Chroma. On a follow-up (history present), a Haiku call rewrites the message into a standalone retrieval query first (v2 behavior, reused from `shared/rag_core`); the first turn uses the **raw** message. The retrieval query is logged (`interactions.rewritten_query`, a `rewrite` `model_calls` row). Recent interactions for the session are carried into the Sonnet messages along with the **original** message so it resolves follow-ups itself — the rewrite only feeds the embedder. No retrieval results → not-found plus redirect.
3. Sonnet **streams** a prose answer with inline `[title](url)` citations (async stream API), emitted to the client token-by-token. Off-domain/unsupported questions are declined in the prose itself.
4. The frontend parses the streamed markdown for links and opens the cited pages as tiles as they appear.
5. After the answer completes, the backend runs the **async highlight** enhancement (default on, non-blocking): parse the finished answer's cited URLs, keep those that are on an allowed host AND in the retrieved source set, fetch each (page cache, concurrent, one Haiku call per page), snap the returned span, and emit a `highlight {url, quote}` event per page.
6. The companion reveals the containing tab/collapsible if needed and highlights the quote in the already-open tile (no scroll), or reports a miss.

> Historical (gated) lifecycle, no longer run: Haiku rewrite → retrieve → structured claim-tagged draft (section 4) → fetch cited pages → per-claim Haiku verify → branch (pass / one informed regen / not-found). Removed because it blocked the first token on a full draft + verification.

### 2.4 Failure handling (removed)

The verify gate, the informed regen, and not-found-on-verification-failure are **gone**. The only not-found is "retrieval returned nothing" (scoped to "I could not find this on the city site," never "this does not exist," routing to a real human contact). Off-domain or unsupported questions are declined by Sonnet in prose. A cited page that can't be fetched or whose span can't be snapped simply yields no highlight for that page — the answer already shipped.

### 2.5 Quotes and highlighting (async, post-answer)

Sonnet paraphrases; it is never asked to quote. The verbatim highlight quote is produced by a Haiku pass over the freshly fetched page text **after** the answer has streamed, so it never delays the answer. For each cited page (claims grouped, page text sent once, pages fetched concurrently) Haiku returns the exact span; the backend Snaps it to a true substring before emitting it. A page that can't be fetched (or a span that won't snap) just gets no highlight.

Three mechanics keep the highlight reliable:
- Snap: models copy imperfectly, so after Haiku returns a span the backend snaps it to the actual fetched text it holds (a quick fuzzy align), guaranteeing the quote shipped is a true substring of the page.
- Normalization parity: the crawler strips `script`, `style`, `nav`, `footer`, `header`, takes the main or article or `.content` region, joins across elements with single spaces, and collapses whitespace with `re.sub(r"\s+", " ", text)`. The stored chunk is a normalized projection, not a literal DOM slice. So the backend's live fetch uses the same extraction (section 9), and the companion applies the same whitespace collapse to live text and searches the same content root before matching. The crawler also injects a `Title:` prefix into some chunks; that text is not on the page and must never be a highlight quote.
- Reveal: cited text can sit in a non-default Bootstrap tab or a collapsed section (the crawler extracts hidden text regardless of CSS). The companion detects the Bootstrap markup and hijacks the show call by clicking the real control (the element with `data-bs-toggle` and the matching target), version-agnostic across Bootstrap 4 and 5, then waits a layout tick before scrolling. Optional future upgrade: convert collapsibles to `hidden="until-found"` so native find-in-page and fragment navigation auto-reveal them, which also benefits residents using Ctrl+F; broadly supported now (Chrome since 2022, Firefox 139 May 2025, Safari late 2025) but not safe for very old browsers, so it is an enhancement, not a dependency.

Companion DOM-miss is a display fallback. If the companion cannot locate the quote live (rare: a JS-built section, or a reveal that failed), it shows the page without a highlight and notes it. Sonnet is not re-run. The highlight is purely additive: the answer and the tiles are already on screen, and a missing highlight degrades gracefully to an opened page.

### 2.6 Transport

WebSocket, because a turn is bidirectional within itself. The Anthropic key never leaves the server. Outbound event types: `narration`, `answer_token`, `answer_done`, `highlight`, `not_found` (plus a `session` envelope carrying the session id, and `error`). Inbound: `query` and the companion-miss `tile_result`. The shell routes answer tokens to the chat module, narration to the live region, and highlight events to the matching open tile.

Protocol contracts:
- **Streamed answer:** `answer_token` events carry real token chunks as Sonnet generates, terminated by `answer_done` whose `answer` field holds the full text.
- **Tiles are opened by the frontend**, which parses the inline `[title](url)` markdown out of the streamed answer. There is **no `open_tiles` event**. Multi-turn lifecycle (a new cited answer replaces the tiles; a reply with no links leaves them) is the shell's responsibility.
- **`highlight {url, quote}`** arrives asynchronously after `answer_done`, zero or more per turn; the shell matches it to the open tile by URL and highlights (no scroll). Absence of any highlight just means no span was found.

### 2.7 Data model (SQLite, WAL, busy_timeout set)

Session history is derived from recent interactions, not duplicated.

- `sessions(session_id TEXT PK, created_at, last_seen_at)`
- `interactions(interaction_id TEXT PK /* uuid4 */, session_id, created_at, user_query, rewritten_query, outcome /* answered | regenerated | not_found */, final_answer, citations JSON, regen_count INT, tokens_in INT, tokens_out INT, latency_ms INT)`
- `model_calls(id INTEGER PK, interaction_id, seq INT, call_type /* rewrite | draft | verify | regen */, model, tokens_in, tokens_out, latency_ms, prompt JSON, response JSON, created_at)`
- `verifications(id INTEGER PK, interaction_id, source_url, claim, verified INT, quote, page_cache_hit INT, fetch_latency_ms, created_at)`
- `retrievals(id INTEGER PK, interaction_id, rank INT, chunk_id, url, score REAL)`
- `page_cache(url TEXT PK, text, fetched_at, ttl_seconds)`
- `rate_limits(key TEXT PK, window_start, count)`

Indexes: `interactions(session_id, created_at)`, `model_calls(interaction_id)`, `verifications(interaction_id)`, `retrievals(interaction_id)`. Every generation is logged in `model_calls` tied to its `interaction_id`. The interaction uuid is surfaced to the frontend for support reference. Keep log tables logically separable so they can move to their own file later if analytics scans contend with the serving path.

### 2.8 Accessibility (target: WCAG 2.1 AA, due April 26, 2027 for Garden Grove)

Most of the WCAG surface lives in the chat module (section 5), which is built to conformance from the start rather than audited at the end. The shell adds: frame `title` on each tile iframe, focus order that does not yank into or lose focus on tile open and close, highlight signalled by more than color with adequate contrast, full keyboard operation of tiles, and `prefers-reduced-motion` gating the morph and tile animations. The embedded city pages are the city's own responsibility and independently in scope. Testing is manual plus automated; automated scanners catch only a fraction of issues, so screen-reader and keyboard passes are mandatory (section 7).

### 2.9 Mobile

Chatbot only, no iframes, no tiles. Citations are links the backend builds with a `#gigi=` hash from the verified quote it already holds, so the user taps to open the city page and the companion highlights there. Standard chat accessibility applies, including descriptive link text. Target-size minimum is good practice but is a WCAG 2.2 criterion, not part of the 2.1 AA mandate.

## 3. Key decisions and tradeoffs

- Subdomain or path plus companion, not a content-rewriting proxy. Removes cross-origin DOM reads and keeps Gigi isolated. Cost: a script on every page (security review, critical path) and a cross-origin framing allowance.
- Stream first, verify never (responsiveness over a pre-answer gate). The grounded, retrieval-fed Sonnet answer streams token-by-token; there is no verify gate or regen. Highlighting is an additive post-answer fetch (cost: per-query fetch + one Haiku call per cited page, off the critical path, mitigated by the page cache).
- Highlighting is best-effort, not a correctness gate. A missing/unsnappable span degrades to an opened page with no highlight; the answer already shipped.
- Handrolled chat module, not Deep Chat or any library. Deep Chat's handler and signals API would have accommodated the custom event-driving, but it is a shadow-DOM component with no WCAG conformance guarantee, and accessibility defects in its internals (focus, live-region announcements, control contrast) are hard to fix from outside. Given the 2027 legal mandate and that the chat surface carries most of the WCAG burden, owning the semantics is worth the build cost. The module is built standalone so the effort is reusable.
- SQLite, not Redis. One file for session, cache, limits, logs; fits the data-local posture. Boundary: single machine.
- Lit, standards-based, small runtime. Animation is more manual than React plus Motion; acceptable.
- Inline `[title](url)` prose citations (not a structured claim-tagged JSON draft). The frontend parses links for tiles; the backend parses them to drive the async highlight fetch. This is what makes true token streaming possible.

Where this plan is opinionated: it is tuned for responsiveness — first token in ~1s, highlighting as a non-blocking enhancement. The earlier low-false-positive verify gate was removed for this; if assurance is later prioritized over latency, reintroduce a gate as an opt-in.

## 4. Structured draft format (REMOVED — historical)

> This format was dropped in the streaming rewrite (see the build note). It forced a full draft before any text could stream. The answer is now streamed prose with inline `[title](url)` citations; tiles come from parsing those links, and highlight spans come from the async Haiku pass. The section is kept only to explain the old claim→source map.

Sonnet emitted the answer as segments, each tagged with the source ids that support it.

```json
{
  "segments": [
    { "id": "s1", "text": "City Hall is open Monday through Friday.", "source_ids": ["src2"] },
    { "id": "s2", "text": "Passport services require an appointment.", "source_ids": ["src5"] }
  ],
  "sources": [
    { "id": "src2", "url": "https://www.ggcity.org/cityhall", "label": "City Hall hours" },
    { "id": "src5", "url": "https://www.ggcity.org/passports", "label": "Passport services" }
  ],
  "abstain": false
}
```

Rules: every factual segment carries at least one source id; an empty `source_ids` on a factual segment is itself a failure to handle; `abstain: true` short-circuits to not-found. Verification marks each source pass or fail; the backend then applies section 2.4 handling.

## 5. The chat module (standalone, WCAG-first)

A self-contained Lit web component that renders the conversation and nothing else. It owns no transport, no tiles, no business logic, so it is reusable in any app and testable in isolation. The Gigi shell drives it imperatively and listens for a single submit event.

Responsibilities:
- Message list, user input, streaming render of assistant tokens, markdown rendering with sanitization (`marked` or `markdown-it` plus `DOMPurify`, since model output is rendered).
- A narration or status affordance backed by an `aria-live` region.
- Citation rendering with click callbacks (the shell decides what a click does, for example open a tile).

Public API (transport-agnostic), roughly:
- `appendUserMessage(text)`
- `beginAssistantMessage()`, `appendAssistantToken(text)`, `endAssistantMessage()`
- `setNarration(text)` routes to the live region and a visible status line
- `renderCitations(items, onClick)`
- `showNotFound(text, redirect)`, `showError(text)`
- emits `submit(text)` when the user sends; the shell forwards it over the WebSocket

WCAG conformance built in, not bolted on:
- Stream tokens visually but announce the completed answer once; never pipe every token into the live region.
- Message list with an appropriate role and each message associated with its sender; new messages do not steal focus.
- Input has a programmatic label, keyboard submit, and an announced disabled state during a turn.
- Visible focus indicators, focus order that keeps the user in control, a keyboard path to the latest message.
- Color is never the only signal; meets contrast on text and controls.
- All motion (typing indicator, autoscroll) gated by `prefers-reduced-motion`.

This is its own undertaking with its own acceptance bar: it passes an axe automated scan and a manual keyboard and screen-reader walkthrough before it is wired into Gigi.

## 7. Testing strategy

Principle: mock the backend at its boundary and prioritize integration and end-to-end over unit. The branch logic, the streaming display, the companion highlight, and accessibility are where defects hide, and they only surface when components run together against realistic event sequences.

### Mock backend
A fixture that emits scripted WebSocket event sequences so the entire client flow runs deterministically without Anthropic, Chroma, or live fetches. Drive it either with the test runner's WebSocket routing (Playwright's `routeWebSocket`) or a small stub WebSocket server that replays fixtures. Each fixture is one scenario's ordered events.

### Client end-to-end (the primary investment)
Tooling: Playwright across the target browsers, with axe-core integrated for accessibility assertions, plus a fixture city page (static HTML with real Bootstrap tabs and known text) served same-origin in the harness so the companion and iframe path are exercised for real.

Scenarios to cover end to end:
- Happy path: answer streams, tile opens, companion highlights the quote.
- Verify fail then regen then success: the failed draft never appears, the regenerated answer does.
- Regen fails: not-found plus redirect, no partial answer.
- Companion DOM-miss: page shown without highlight, noted.
- Hidden content: quote inside a non-default Bootstrap tab is revealed, then highlighted.
- Abstain: chunks support nothing, not-found.
- Mobile: no tiles, citation is a `#gigi=` link, companion highlights on the destination.

Accessibility is a first-class e2e concern, not a separate afterthought:
- Keyboard-only walkthrough of a full turn including opening and closing a tile.
- Screen-reader announcement checks (axe for the automatable parts, a manual pass for the rest), focus order, and reduced-motion behavior.

### Chat module in isolation
Because it is standalone, it gets its own e2e and a11y suite driven through its public API with scripted streams, run before it is embedded. This is its acceptance gate (section 5).

### Backend integration
Integration tests that mock the Anthropic SDK at its boundary (stubbed or recorded responses) and run against a small fixture Chroma collection, exercising the orchestrator's branches deterministically: pass, verify-fail then regen then pass, regen-fail then not-found, abstain. The point is the branch logic and the logging writes, not the models.

### The few unit tests worth writing
Only the gnarly pure functions: fuzzy match and snap, the normalization that must match the crawler, and the claim-map selection that decides which segments failed. Everything else is covered better by the integration and e2e layers above.

## 9. Shared library and code reuse

One copy of any logic that must not drift between indexing, the Gradio harness, and the new backend.

- `shared/rag_embeddings.py` (existing, unchanged).
- `shared/extraction.py` (new, from the crawler): used by the crawler at index time and the backend at verify time, so normalization is identical (section 2.5).
- `shared/rag_core.py` (new, from the chatbot): rewrite, retrieval, formatting, generation, no UI dependency.

Consumers: `crawler/website_crawler.py` imports extraction and embeddings; `gradio_app.py` is a thin UI over rag_core, kept for testing; the FastAPI backend imports both and adds the agentic loop, the structured draft prompt, SQLite logging, and the WebSocket protocol.

The decisive reason to share extraction rather than reimplement: verification and highlighting line up only if the verifier reads text normalized the same way the chunks were built. Sharing removes that risk by construction.

## 11. Risks and open items

- Log PII under AR 2.16. Logging raw user queries makes the interaction log a PII store even though crawled pages have none, because residents volunteer PII in free text. Requires a retention policy, access controls, and likely redaction on the query field. Reference: AR 2.16 (Cloud Computing Services Policy), https://internal.ggcity.org/policies.
- SSRF via cited URLs. The streamed answer can contain arbitrary `[text](url)` links; the backend fetches cited pages for highlighting, so it MUST restrict outbound fetches to an allow-list of hosts (`ALLOWED_FETCH_HOSTS`, default `ggcity.org`) and to URLs already in the retrieved source set. Never fetch a raw model-emitted URL unguarded.
- Streamed answers ship before any verification. The deliberate trade for responsiveness (verify mode was removed): the grounded prose answer is trusted and streamed immediately, with highlighting as an additive post-answer check, not a gate. If low-false-positive assurance is needed later, a gate would have to be reintroduced as an opt-in, accepting the latency hit.
- Handrolled chat means the WCAG burden is yours. That is the deliberate trade for control; budget the audit and remediation, and treat section 5's acceptance gate as real.
- Framing-header approval. If the city cannot allow the Gigi origin to frame the site, the desktop tiling falls back to the mobile links-only experience.
- Custom Highlight API support. Broadly supported in current Chromium and Safari; verify on the browsers residents use and keep the span fallback.
- Server-rendered vs JS-rendered divergence. Backend-fetched HTML can differ from the rendered DOM on JS-built sections; Drupal is mostly server-rendered, but handle the companion miss path.
- Bootstrap version differences. Reveal by clicking the control is version-agnostic; if you switch to the Bootstrap JS API, branch on 4 vs 5.
- High load deferred. Steady state at the expected scale is light, but an emergency inverts that assumption; revisit backpressure and pre-caching before any high-traffic event.
- Single-machine SQLite boundary. Fine at pilot scale; multi-machine needs a different store.
